| 场景类名 | 内容 | OCR 依据 |
|---|---|---|

| `Li13_8_Z2_QuMian` | 3D 反例曲面 z₂：沿两条坐标轴贴住候选平面，沿 45° 脊线 z = ρ/2 线性顶穿 | p321–p322 例13.8 |
| `Li13_8_Z1_DuiBi` | 3D 对照曲面 z₁ = \|xy\|：偏导同样是 0，但脊线 z = ρ²/2 与平面相切 → 可微 | p321–p322 例13.8 |

**这个场景顺带纠正了一条错误的几何直观**（含 Claude 自己上一轮口头讲的）：
「偏导存在只保证两条切线存在，但它们不共面」—— **错**。两条截痕切线都过同一点 P₀，
方向 (1,0,f'x) 与 (0,1,f'y) 恒线性无关，**永远共面**，张成的平面恰好就是候选切平面
`z = z₀ + f'x·Δx + f'y·Δy`。偏导存在的真正含义是「候选切平面**一定存在**」，
可微的含义是「曲面**真的贴着**它」（误差 o(ρ)）。两者差在后半句，不在前半句。
`verify_li13_8.py` 第 1 组就是验证这条。

### 等值线是什么（`scenes/li13_20.py`，2026-09-21 新增）

起因：用户问「例13.20 为什么能把目标 `(b-a)³/6` 直接换成 `(b-a)`？它们是两个完全不同的
函数啊」。症结是**没建立「等值线」的图景**，于是要求用 3D 讲，并且「全方位多角度、时长长一点」。

核心设计：**等值线 = 用水平面切曲面 → 切痕 → 从正上方俯视看到的线**。
关键一步是把相机转到正上方俯视：三条切痕变成一族平行直线，这就是等值线的全部含义。
换成 h=(b-a)³/6 之后，曲面形状变了、切面高度从 1.00 降到 0.17，**但俯视图纹丝不动**。

| 场景类名 | 内容 | 时长 |
|---|---|:--:|
| `DengZhiXian_LaiLi` | 等值线的来历：绕场一周 → 三刀（每刀都演示「切 → 落到底面」）→ 换角度 → 再绕场 → 淡出曲面 → **转到正上方俯视** → 转回侧视对照 | 74s |
| `DengZhiXian_TongYiZu` | 换成 h=(b-a)³/6 之后：曲面变形、切面高度 1.00→0.17，两条影子**完全重合**（粗虚线打底 + 细实线压中）→ 俯视收尾 | 60s |

数值依据：`数学题验证/verify_13_20.py`（14/14）+ `verify_13_20_levelset.py`（11/11）。
配图（matplotlib 版）：`工作区\数学\图像\例13.20_单调替换_等值线.png`。

**本场景踩出并修掉的 4 个坑**（都是查帧肉眼发现的，程序化自检全部报「通过」）：

1. **不要铺地面网格**。manim 的 cairo 渲染对「大 `Surface` vs 一堆网格线」的深度排序
   **不可靠**——整个 Surface 只按中心点排一次序，网格会穿透曲面，两者糊成一块平板，
   「曲面悬在地面之上」完全看不出来。改成不画网格，靠「曲面半透明 + 最后淡出曲面」露出底下的线。
2. **z 轴不能太短**。首版 `lengths=(6.4,6.4,4.0)` 配 `z_range` 5.4，z 方向被压缩 2.7 倍，
   45° 的斜面在屏幕上的视坡度只剩约 0.5，看着像平的。拉到 `(4.4,4.4,6.2)` + `zoom=0.85`
   才读得出「这是个斜坡」。但也不能拉过头（试过 7.2，四角溢出画面）。
3. **多条切痕要一色一条**。首版三条同色，俯视时说不清哪条是哪个高度。
4. **「两条线重合」在俯视图里会只剩一条**，反而看不出有两条。改成**粗虚线打底 + 细实线压中**
   （细线抬 z=0.02 叠在上面），重合才有「双层」的视觉证据。

另：3D 坐标轴名（`axis_labels`）在俯视时会飘到左上角撞分区文字（实测 0.025 单位²，
低于报错线所以没被拦），**转俯视前先 `FadeOut(labs)`、转回来再 `FadeIn`**。

### 这个场景踩出来的 6 个坑（全部靠**查帧肉眼**发现，程序化自检一个都没抓到）

**1. 相机方位角决定阶梯读不读得出来 —— 这是最大的一条。**
n=3 的柱高是 1.6 / 1.32 / 1.03，而底面只有 3.2 见方。用原来的
`phi=68°, theta=-58°`，**前排柱把后排几乎全挡住**，屏幕上只从缝里露出几块
**三角形**柱顶 —— 几何完全正确，但根本数不出"9 根小竖条"，概念就废了。
扫了四个角度逐帧比对（临时脚本 `scenes/_t_bar.py`，已删；做法是给 9 根柱各一个
不同颜色，就能看清每块可见面属于哪根）：

| phi / theta | 结果 |
|---|---|
| 68° / −58°（原值） | 三角形碎片，读不出 |
| 52° / −58° | 仍是三角形碎片 |
| **52° / −20°** | **9 个柱顶全是完整四边形，一眼数得出** |
| 40° / −58° | 三角形碎片 |

**关键变量是方位角 theta，不是仰角 phi** —— 转到 −20° 时视线顺着网格方向看过去，
每一排的顶都露出来。曲顶 `f = 1.6 − 0.25r²` 是旋转对称的，换方位角对它零损失。

**2. `shade_in_3d` 不设的话，柱子会全部画在最上层。**
`ThreeDCamera.get_mobjects_to_display()` 里：

```python
def z_key(mob):
    if not (hasattr(mob, "shade_in_3d") and mob.shade_in_3d):
        return np.inf          # 不参与 3D 排序 -> 永远画在最上层
    return np.dot(mob.get_z_index_reference_point(), rot_matrix.T)[2]
```

两条推论：① **只有顶层 mobject 参与排序**，几十根柱塞进一个 `VGroup` 就等于放弃
排序（README 约束 6 那条「整个 Surface 只按中心点排一次序」说的就是这个现象）；
② `make_bar()` 里 `g.shade_in_3d = True` 不能省。

**3. 柱体的排序键要用【底面中心】，不能用质心。**
`z_key` 默认取 `get_z_index_reference_point()`，即质心。相机仰角 phi 下，世界 z 轴
在相机空间仍占 `cos(phi) ≈ 0.62`（phi=52°）的分量，于是**柱越高 -> 质心越靠近相机**，
一根矮但在前面的柱会被一根高但在后面的柱压住。
对**铺在平面上的一排方柱，正确的排序键只有平面位置，不含高度**，故 `make_bar()` 里
把 `get_z_index_reference_point` 覆盖成底面中心。

**4. 半透明曲顶会把底面上的一切洗成蓝灰。**
曲顶 `fill_opacity=0.5` 盖在 z=0 之上，首版高亮片本该是橙色、结果被洗成**灰白色**。
做法：底面作业期间（分 / 取 / 乘）把曲顶压到 `0.14`，柱子要往上长时再恢复到 `0.42`。

**5. 柱体必须实心。** 首版侧面给 `fill_opacity=0.5`，9 根柱互相透视，
在屏幕上糊成一团橙色。侧面用暗一档的 `SIDE_DARK (#8C4A1A)` + `0.88`，
顶面 `WARM` + `1.0`，台阶才立得起来。

**6. 叠字检测查不到「文字 vs 3D 物体」。**
`LayoutMixin` 只算文字两两相交面积。柱体长高后顶部顶进了 `top_l` 那条解说带
（「真值 12.0149」被橙色柱子压住），**报告是 0 叠字**。只能靠查帧。
改法：阶梯段起解说一律走 `bot_l`。另：`bot_l` 锚点在 y=−3.58，堆叠超过 3 行
（约 1.5 单位）就会长到 y≈−2 撞上曲顶底边，所以总结只放 3 行。

另两条小的：`FadeIn` 自己会把对象加进场景，**别提前 `self.add()`**（会闪一帧全不透明，
同约束 7b 的 `pin()` 坑）；曲顶那层 `Surface` 与柱体的交接**必须交叉淡入淡出**，
不能先 `FadeIn(surf)` 再 `FadeOut(bars)` —— Surface 整体只有一个 z_key，
中间那几帧会出现「曲面被前排柱挡住」。

### 这一轮 verify 脚本钉住的三件事

1. **例14.9 的答案手算错过。** 曾把 `arctan(1)` 当成 π/3，得出 π ln2/(6√3)，
   比正确值 **大 4/3 倍**。正确是 `π/(4√3)`，乘起来 `√3πln2/24 ≈ 0.15715374`。
   verify 第 30 项专钉这一条，场景里也专门讲了一句「这里最容易错」。
2. **例14.5 不是「书上说选 B」。** 四个选项在 f ≡ 1 下各积一遍：
   (A) −0.570796、(B) +0.570796、(C) +2.141593、(D) +1.000000，只有 (B) 等于 π/2−1。
3. **蒙特卡洛抽样框首版设小了。** 取 [0,√2]²（盯着外椭圆过 (√2,0)/(0,√2)/(√2,√2) 定的），
   算出面积 0.5677 对不上解析 0.8555。根因：外椭圆 `x²+y²−xy=2` 的**最大 x 不在对角线上**，
   而是 x=2y 处的 `2√(2/3) ≈ 1.633 > √2`，框小了把右边一整块漏掉。
   改 [0,2]² 后 MC 0.855267 vs 解析 0.855469。

### 这一轮踩出来的坑（8 条，其中 6 条只有查帧能发现）

**1.（自检抓到）`place(..., "top_r")` 的说明块会盖住解说带。**
锚点在 y=2.80、块往下长，5 行约 2.0 单位高 —— 正好压在 `say2` 的解说带 y=2.55 上。
实测重叠 **0.975 / 1.706 单位²**，直接 `AssertionError` 中断渲染。
**规矩：top_r 有说明块在场时一律不调解说，先 `FadeOut` 再 `say2`。**

**2.（自检抓到）读数标签别沿对角线各贴各的。** 三个弧长读数首版各贴着自己的弧摆，
两两相交 0.068 单位²（低于 `OVERLAP_FAIL=0.6`，只记录不中断）。改成一列排开。

**3.（查帧抓到）「文字 vs 图形」的对撞，`LayoutMixin` 完全查不到。**
它只算「文字两两相交面积」，图形是 `VMobject`/`Polygon`，不在检查范围内。场景四首版：
- 右边第一象限方区 `O2=(1.75,-2.45), S2=2.30` 一路铺到屏幕 (7.04, **2.84**)，顶穿标题带、
  压住 top_r 说明块；
- 左边曲线图占 y∈[-2.45,−0.40]，正与 `bot_l` 说明块（y∈[−3.58,−1.08]）压在一起。

两种情况**自检报告全是空的**，抽帧一看就露。改法：方区缩到 `O2=(2.70,−2.95), S2=1.55`
（方区右上角收到 (5.96,0.31)，与 top_r 块的下沿 0.81 留出空隙）；曲线图整块抬到
y∈[−1.4,0.3]；说明块从 5 行压到 3 行。**同约束 6/7 的道理：新增大幅面图形后必须抽帧。**

**4.（查帧抓到）标签右端顶到画面边。** 场景一「径向边长 = Δr = 0.5」摆在放大矩形右侧，
右端到屏幕 x≈**6.99**，画面右边界 7.11 —— 只剩 0.12 单位，再长一个字就出画。
改成两条边长标签都摆到矩形下方居中。

**5.（查帧抓到）极坐标网格里 `O` 被射线糊住、`y` 被射线末端顶住。**
12 条射线全过圆心，`O` 贴原点摆会糊成一团白 —— 挪到 `DL*0.5`，正好落进 210°/240°
两条射线之间的空隙；`y` 从 2.22 抬到 2.45（θ=π/2 的射线与 y 轴重合，一直画到 r=2）。

**6.（查帧抓到）坐标轴的放大倍数 S 会决定它横穿多远。** 场景二首版 S=3.40，x 轴箭头
伸到屏幕 x=+5.43，压到右侧说明区下面；改 2.0 能渲但图偏小、上半屏空得多；最终
**S=2.4** 两头都合适。另：箭头别停在积分区域右边上（x=π 处会和 D 的竖边糊在一起），
`XSPAN` 从 3.30 提到 3.45 让箭头多伸出去一截。

**8.（查帧抓到，本轮最值得记的一条）极坐标助手 `p(r, th)` 收的是（半径, 角度），
不是直角坐标 —— 传错参数会把标签默默丢到圆心。**
场景一的坐标轴标签写成 `self.p(0, 2.45)`，本意是「y 轴上方 2.45」，实际是
「半径 0、角度 2.45 rad」= **圆心**。于是 `y` 从第一版起就一直糊在 12 条射线的
汇聚点上，谁也读不出来。改 `self.p(2.45, np.pi/2)` 才对。
两个原因让它特别隐蔽：
- `self.p(2.42, 0)`（x 标签）**恰好是对的** —— θ=0 时极坐标退化成直角坐标，
  所以「x 看得见、只有 y 不见」，很容易误判成颜色/对比度问题；
- `LayoutMixin` 不报，因为 `y`(y∈[−0.68,−0.43]) 与 `O`(y∈[−1.03,−0.78])
  的包围盒在 y 方向刚好错开 —— **几何上没重叠，只是位置错得离谱**。

**抓它的唯一办法是把那块裁出来放大看**（`PIL.crop(...).resize(..., NEAREST)`）。
1080p 整帧缩到终端里看，一个灰色的 `y` 混在白色射线上根本分辨不出来。
**凡是用自定义坐标映射函数摆的文字，都要裁图放大确认一次。**

**7. `guard()` 又拦下一次，另配了字形表全量检查。**
`₀`(U+2080) 和 `⇒`(U+21D2) 混进了解说文本，渲染前被 `guard()` 拦下并给出替换建议。
另外写了个一次性检查：用 fontTools 读 `C:\Windows\Fonts\msyh.ttc` 的 cmap，

结果除换行符外全覆盖。**比肉眼猜「这个符号有没有字形」可靠得多**，值得固化成脚本。

## 第14讲 二重积分·轮换对称性（`scenes/erchong3.py`，2026-09-25 新增）

用户点名要的：「张宇讲的什么大面包交换 x 与 y」。

**书上出处**：OCR `p352` 的手写注释 —— **「谁动了我的面包！答：没有动 => 体积不变」**。
**张宇原话**（TTS `03.第14讲一、概念、性质与对称性03`）：
「二重积分是一个什么来着？各位，**大面包**很好，大面包由什么组成的呢？打**小薯条**」
「**谁动了我的面包？没有动！没有动！没有动！**面包没动，体积是不变的」

**几何本质（场景要讲的那一件事，也是唯一正确的那句）**：
交换 x 与 y **= 把整个立体关于平面 y = x 作镜像**。镜像（反射）是等距变换，**体积必然不变**；
而底面 D 镜像后还是不是它自己，取决于 D 是否关于 y = x 对称。
——注意别讲成「每个点的高度跟着对称点走」，那是错的；这是**变量重命名** + **镜像**，
不是逐点配对。

数值依据 `数学题验证/verify_lunhuan.py`（**11/11 PASS**，sympy + scipy 双重）。
模型：`D` = 单位圆盘，`f(x,y) = 1.3 + 0.5x − 0.15(x²+y²)`，`f* = f(y,x)`；
`∬f dσ = ∬f* dσ = 49π/40 = 3.8484510006`；`f|D ∈ [0.65, 1.65]` 恒正。

| 场景类名 | 内容 | 时长 |
|---|---|:--:|
| `ErChong3_LunHuanDaMianBao` | 圆盘底 → 小薯条 → 大面包 → 拿平面 y=x 照镜子 → 面包翻身、底不动 → 体积不变 → 用途 | 58s |

verify 钉住的三件硬事：

1. **两个积分精确相等**（sympy 极坐标 `49π/40`，scipy 独立复核 `|Δ| = 4.4e-16`）。
2. **反例**：把 D 换成**右半圆盘**（关于 x 轴对称，但**不**关于 y=x 对称），
   两边差 **1/3**（2.2575588 vs 1.9242255）。**这条证明「D 关于 y=x 对称」这个前提
   不是装饰，是真在起作用** —— 只讲"交换字母值不变"会漏掉它。
3. **课本用例**：`∬_D (a√f(x)+b√f(y))/(√f(x)+√f(y)) dσ = (a+b)/2 · S_D`，
   取 a=1,b=2 数值 = 3π/8 = 1.1780972451；另逐点验证 `g(x,y)+g(y,x) ≡ a+b`（2000 点，偏差 < 1e-12）。

### 这一轮查帧肉眼抓出的 6 个坑（程序化自检一个都没抓到，`_layout_report.txt` 全程为空）

**1.（几何错，最严重）y = x 与圆的交点必须用 R/√2，不能写 R。**
首版 `diag_line` 端点写成 `(±R, ±R)`，那是**距离 √2·R** 的点 —— 在斜视角下投影出来
**比圆的轮廓还长 41%**，屏幕上看着像「积分区域延伸到圆外」，几何上就是错的。
正确交点 `(±R/√2, ±R/√2)`。
**抓它的唯一办法是裁图放大**（`PIL.crop(...).resize(..., NEAREST)`）：整帧缩到终端里，
那条线只比圆宽一点点，肉眼看不出来。**同约束「极坐标助手传错参数」的道理 ——
凡是用自定义坐标映射摆的几何元素，都要裁图确认一次。**

**2.（最隐蔽）3D 场景里的平面插图必须 `add_fixed_in_frame_mobjects`。**
右下角那张 2D 俯视图首版忘了钉，结果被 ThreeDScene 当普通 3D 物体：
**圆按相机透视转成了一个斜的细椭圆**，标签跟着歪、还甩到画面外。
`pin()` 内部就是干这个的；要自定义位置时，先 `move_to` 再 `add_fixed_in_frame_mobjects`。

**3. 只画曲面 = 一张飘着的薄饼，必须补侧壁（面包皮）。**
首版只有一个 `Surface`，屏幕上就是个"飞碟"，"大面包"这个比喻整个垮掉。
补 `crust_wall()`（沿圆周 z=0 到曲顶之间 n 个小四边形）之后才立得起来。
**侧壁必须拆成 n 条、逐条加进场景**：包成一个 `VGroup` 再 `FadeIn` 就只剩一个 z_key，
排序全废（同约束 6）。`Transform` 同理，要写成 `*[Transform(a,b) for a,b in zip(c1,c2)]`。
排序键用**底面中心**（同 `make_bar`，见坑 3）。

**4. 极坐标曲面的网格全汇在圆心 → 屏幕上是一团「星芒」，顶面看着像圆锥尖。**
`resolution=(10,48)` 配 `BLUE/#2C6E86` 两个反差大的色块，48 条经线汇聚到极点。
改 `(8,36)` + 两个相近的蓝 + 细描边后，才读得出是「曲面」而不是「锥面」。
**注意这是极坐标参数化的固有现象，不是 bug** —— 只能弱化，消不掉。

**5. 实心立体把底面完全盖住 ——「底面没动」在三维里没得看。**
面包正好压在 D 上，圆和 y=x 线全被挡住，而这一拍要讲的偏偏是「看底下，圆盘没动」。
解法：右下角补一张**永远不动的 2D 俯视图**（`top_view_inset()`），它不变就是 D 不变。
**这条是一般性教训：要论证「某物没变」，得先让那东西看得见。**

**6. 标签太长会出画。**
「D 的俯视图（x、y 换位置，它不变）」18 字，居中摆在 x=5.45 时右端到 **x≈7.35**，
而画面右边界只有 **7.11**。缩短成「D 的俯视图」即解决。
（`LayoutMixin` 报了 0.225 / 0.100 单位² 的轻微相交 —— 低于 0.6 的中断线，
只记录不中断，**正是那种"渲染能过但已经不对"的情况**。）

另：`guard()` 这一轮又拦下两次 —— 裸 `<`（`<=` 要写 `&lt;=`）和本机无字形的 `⇒`（改 `=>`）。
**别嫌它烦，两次都是它替我省了一轮重渲。**

## 七条环境硬约束（都是实测踩出来的，别「顺手清理」）

### 1. 没有 LaTeX，`MathTex` 不可用

本机无 MiKTeX/TeXLive，`latex` / `dvipng` / `dvisvgm` 都不在 PATH。实跑 `MathTex`
抛 `FileNotFoundError: [WinError 2]`。所以**全部公式只能用 `Text` / `MarkupText` + Unicode**。

`MarkupText` 的 Pango 标记可用，试验证过：`<sub>`、`<sup>` 都正常，
所以下标直接写 `x<sub>0</sub>`，不必手工拼合。

### 2. 字体必须用 Microsoft YaHei，且 Pango 自动回退在本机不生效

| 字体 | 中文 | ∂ √ ∫ ∞ | 希腊字母 | ≈≠≤≥→ | ×·±− | ²³⁴ⁿ |
|---|---|---|---|---|---|---|
| **Microsoft YaHei** | 有 | 有 | 有 | 有 | 有 | 有 |
| SimHei | 有 | **缺 ∂** | 有 | 有 | **缺 −** | **缺** |
| Cambria Math | **无中文** | 有 | 有 | 有 | 有 | 有 |

实测：`Text("∬", font="SimHei")` 渲染出来是**实心方块**，且与 `Text("∬", font="Arial")`
像素完全一致（IoU = 1.000）——说明没有回退到 Cambria Math。**不能指望回退，必须选一个
覆盖全部所需字形的字体。** Microsoft YaHei 正好一个字体全覆盖。

注意：项目里 matplotlib 的绘图脚本（`math-graph` 技能）用 SimHei 是可以的，因为
matplotlib 会自己回退；manim 不会。两者不能照搬。

### 3. 5 个符号本机无字形，禁用

| 符号 | 改用 |
|---|---|
| `∬` | `∫∫` |
| `⇒` | `=>` |
| `↛` | `≠>` |
| `∉` | 文字「不属于」 |
| `∘` | `o` |

还有 Unicode 下标 `₀₁₂ₓᵢⱼ` 也不可用，改用 `<sub>0</sub>` 这类标记。

`scenes/_common.py` 的 `guard()` 会在渲染前拦截这些字符并抛错——因为 Claude Code
无视觉能力，看不了成片，只能靠程序化检查兜底。

### 4. `manim.cfg` 两个坑

- **必须纯 ASCII**。manim 用系统默认编码（本机 GBK）读 `manim.cfg`，写中文注释会直接
  `UnicodeDecodeError: 'gbk' codec can't decode byte ...` 启动失败。
- **`renderer` 必须是 `cairo`，不能写 `opengl`**。写在 cfg 里的 `renderer = opengl` 会让
  manim 把 3D 对象解析到 OpenGL 类层级，那里 `Sphere` / `Dot3D` / `Dot` 没有 `z_index`、
  `Line3D` 没有 `fill_color`，碰到的场景一律 `AttributeError` 崩掉。同样的渲染器用命令行
  `--renderer=opengl` 传反而正常——不依赖这个不对称，统一用 cairo。

### 5. `run.ps1` 必须带 UTF-8 BOM

本机是 Windows PowerShell 5.1，读 `.ps1` 时若没有 BOM 就按 GBK 解码，文件里的中文
（注释和提示语）会全乱，进而报一堆「缺少 }」「字符串缺少终止符」的假语法错误。
**改动 `run.ps1` 后务必用 `utf-8-sig`（带 BOM）保存**，并重新跑一次语法检查：

```powershell
$e=$null
[System.Management.Automation.Language.Parser]::ParseFile('<路径>\run.ps1',[ref]$null,[ref]$e)
if($e.Count -eq 0){'语法 OK'}else{$e | ForEach-Object{$_.Message}}
```

本机执行策略是 `RemoteSigned`，**本地脚本可直接跑，不需要 `-ExecutionPolicy Bypass`**。

### 6. 文字一律用 `place(mob, "分区")`，不要用 `to_corner()`

首版五个场景**全部**出现文字叠字（最大重叠 1.7 单位²），根因就是 `to_corner(UR/DL/DR)`
把文字顶到 y≈3.5，正好撞进标题带。

`_common.py` 把画面切成互不侵占的分区，所有文字按分区摆：

```
┌────────────── title ──────────────┐   y ≈ 3.3
│ top_l                    top_r    │   y ≈ 2.8 往下长
│              mid                  │   y ≈ 0.1
│ bot_l      bottom      bot_r      │   y ≈ -3.6 往上长
└───────────────────────────────────┘
```

同一分区一次只放一组文字——要换内容就先 `FadeOut` 再放新的，不要叠着加。
需要手动微调位置的（如贴着图形的箭头标签），用 `add_fixed_in_frame_mobjects` 挂上去再
自己 `next_to`，**不要再调一次 `pin()`**：`pin()` 会把它重新拉回分区锚点，
两组文字就会精确重合。

配套的自检：`LayoutScene` / `LayoutThreeDScene` 在每次 `wait()` 前算一遍当前画面上所有文字的
包围盒两两相交面积——Claude Code 无视觉能力看不了成片，这是唯一能自动发现叠字的手段。
报告写到 `_layout_report.txt`（manim 的控制台会把长行折断加边框，直接 print 抓不出来），
超过 0.6 单位² 直接抛 `AssertionError` 中断渲染。

两个坑：`Text.get_opacity()` 在本机可能返回 `None`，不能直接拿去比大小——
首版检测器就是在这行静默崩掉、一个告警都没报；另外新增或改完场景，**先用 `-Quick` 跑一遍
看 `_layout_report.txt`**，别等 1080p 渲染完才发现叠字。

### 7. 3D 场景的标题必须用 `title3d(self, ...)`；`pin()` 要紧贴着动画

两条都是 2026-09-19 查帧时肉眼发现的（此前假设没有视觉能力，从未发现）。

**7a. `title()` 在 3D 场景里不能用（会被相机压扁）。** ThreeDScene 里不钉住的话，
文字是放在 3D 空间的，相机会按透视把它压成一条斜的细线（首帧几乎成一条水平线），
还会被曲面挡住。**修复前 2026-09-17 版三个 3D 场景的标题全部不可读。**

```python
# 3D 场景
self.play(Write(title3d(self, "例13.8 ...")), run_time=0.9)   # 对
self.play(Write(title("例13.8 ...")), run_time=0.9)            # 错：字会歪
```

**7b. `pin()` 是「立刻」把对象加进场景的，不是等动画。** 所以它必须紧挨着它自己的
`FadeIn` / `Write`，中间不能插别的 `self.play()`，否则那段动画里文字已经全亮着——
表现为「字幕提前几秒出现」。正确写法：

```python
self.play(Create(lx), Create(ly), run_time=0.9)
p1 = pin(self, stack(...), "top_l")      # 紧挨着下一行
self.play(FadeIn(p1), run_time=0.5)
```

**顺带一条 LaTeX 陷阱**：`ax.get_axis_labels()` 默认生成 MathTex；
`axis_config={"include_numbers": True}` 会走 `DecimalNumber`，而 `DecimalNumber`
内部也是用 MathTex 造数字模板的。**两个都会触发约束 1 的崩溃**。坐标轴刻度与轴名
一律自己用 `T()` 造（见 `scenes/li13_8.py` 场景一）。

注意这与项目其它产出是**故意不同**的：matplotlib 图（`math-graph` 技能）走「暖橙 `#d97724` +
白底」因为要打印进讲义；manim 视频走黑底因为要在屏幕上看。**两边颜色别互相照搬**——
白底那套（`#1a56a8` 深蓝、`#b23a3a` 暗红、`#222222` 墨色字）放到黑底上会糊成一团；
深底那套（`#58C4DD` 亮蓝等，取自 manim 自带 3b1b 调色板）放到白底上又会太浅。

深色主题的取色要点，改配色时留意：背景 `#000000`、正文 `#EAEAEA`、
**坐标轴要提亮**（`#8C8C8C`，深底上太暗看不见）、**网格要压暗**（`#2E2E2E`，深底上太亮喧宾夺主）。
